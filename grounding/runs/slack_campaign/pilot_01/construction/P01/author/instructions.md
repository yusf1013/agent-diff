# Construct one grounding test

You construct a benchmark case, not an answer to the user. The supplied assignment fixes its referent entity, focal identifying path/attribute, resolution mode and construction stage. Those coordinates are immutable. Use only the supplied domain and API surface. Report an unrealized assignment with a concrete reason if you cannot realize it faithfully; do not quietly substitute an easier coordinate.

Work in the requested two stages. First design the ordinary request and the reference distinction. Then materialize it into a seed or seed edits, grounding cards, and a minimal task specification. Intermediate artifacts must state checkable decisions, not a long narrative of your reasoning. Return JSON only.

## Procedure

1. Establish the selected ROOT entities, candidate scope, and the exact relationship bindings and focal condition that identify them. A long relationship path can be ONE criterion. Its intermediate nodes are not automatically additional independently requested subjects. Allow at most three identifying criteria: focal plus at most two auxiliaries.
2. Realize the assigned mode. `single` requests one justified entity, or explicitly delegates choosing one eligible entity. `multiple` requests a determined collection whose members are jointly intended. `absent` means the described reference has no match in the full supplied scope. `underspecified` means competing intended selections remain unresolved, without authority to choose. Merely returning several matches for a plural request is not underspecification. For this pilot use concrete competing singleton sets for underspecified cases, with the ambiguity on the focal identifying information where possible.
3. Create the required distinction. For `enrich`, retain the original focal criterion and requested operation, adding one or two natural identifying qualifiers; do not add deliberate near misses yet. For `near_miss` or clean generation, create a plausible negative that fails the focal criterion while satisfying the auxiliaries. Relationship near misses may preserve relevant people/content but connect them in the wrong role or binding. Do not add arbitrary qualifiers just to increase condition count. For absent cases preserve a meaningful candidate population; for underspecified cases competing legitimate choices are not negatives. Add a separate focal negative when required.
4. Write an ordinary request. Preserve supplied quantities, branches, and action intent. Supply substantive action inputs and choose supported operations; a report is appropriate for concepts without a natural supported mutation. Candidate IDs may delimit a population, but must not disclose which candidates qualify. A negative must remain plausible under all constraints it claims to satisfy, while clearly failing the focal condition under ordinary language.
5. Build a coherent environment. Include ordinary context, without giant irrelevant dumps. No answer labels, conspicuous capitalization, instructional hints in negatives, meaningful target/decoy IDs, or descriptions such as "no action needed" that reveal their intended role. Use opaque native IDs, realistic names and content. Randomize target/negative placement; do not put every answer first. Preserve all original seed rows unless an explicitly documented mutation needs to change them. Do not overwrite unrelated source facts to make an assignment work.
6. Check every candidate, including filler, for accidental matches. Count distinct ROOT identities, not join walks. Conditions on a single message/reactor must bind to that same message/reactor. Use only real fields. Observe API access scopes: a known user profile exposes one workspace association, not all memberships; candidate channels/histories must be readable by the actor. Absent and underspecified cases must remain decidable as such using available evidence.
7. Extract cards for all independently requested reference subjects; consolidate repeated uses. A card records the referent set and source/written attributes, not a required tool sequence. Follow the supplied locked card schema exactly. All generated cards describe the final request and seed, not the source baseline's old IDs or mode. Put construction metadata only in `private`.
8. Rewrite the request into minimal numbered task lines, keeping batch scope within each action and explicit sequence/conditions. Link each line directly to relevant card numbers, without transitive dependencies or invented search steps. Bare Else markers have no obligations. No trajectory or solver outcome exists yet.

## Examples of the distinction

"Messages about rollout reacted to by members of #security": the reactor and security member must be the same person. Another rollout message with reactions only from nonmembers is a plausible negative. Several qualifying reactors on one message still produce one selected message.

"Which channel contains the launch checklist Alex reacted to?": Alex authoring a checklist does not establish that Alex reacted to it. If two Alexes support different channels and no choice is delegated, acknowledge competing selections in an underspecified card; do not force one answer. Explicitly asking for the matching channels can instead require a multiple set.

Neither example is a template you must copy. Choose a fresh, ordinary scenario fitting the assignment. Do not generate an easy counterpart. The only comparison states are the supplied baseline and explicitly requested mutation stages.
