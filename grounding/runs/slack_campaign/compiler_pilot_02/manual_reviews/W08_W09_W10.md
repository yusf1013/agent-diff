## W08 — remove an actor-owned reaction through the author's channel membership

> Remove my fire reaction from the message posted by the member of the channel about launch readiness.

Route: **Reaction → Message → User → Conversation Membership → Conversation**.
The [writer](../construction/W08/story.md) identifies Nina as the actor and these
five reaction roots:

| Reaction | Relevant facts | Role |
|---|---|---|
| Nina's 🔥 on Kevin's message | Kevin belongs to #product-launch, topic “Launch readiness plan” | Match |
| Nina's 👀 on the same message | Same author/membership | Wrong emoji |
| Sam's 🔥 on the same message | Same author/membership | Wrong reactor |
| Nina's 🔥 on Priya's message | Priya belongs only to #design-crew | Wrong author membership |
| Nina's 🔥 on Elena's message | Message is in #product-launch, but Elena belongs only to #marketing-updates | Location is not author membership |

The [first compilation](../construction/W08/compiled-1.json) supplies six users,
four channels, six messages and six reactions. Its selector preserves ownership,
emoji and the full relationship chain. Both the original
[mechanical check](../construction/W08/checks-1.json) and this audit's replay select
exactly Nina's fire reaction on Kevin's message. Wrong-emoji and wrong-reactor rows
are instantiated in the environment even though scope filters exclude them from
the selector's narrower candidate population. They were not dropped from the test.

The reviewer spent its entire 5,000-output-token allowance on thinking and emitted
no final answer. The [thinking summary](../construction/W08/reviews/attempt-1/reviewer/turn-01/thinking.txt)
repeatedly checks the same joins, scope and uniqueness and tends toward a
pass/strong assessment. That is not a completed review, and the pipeline did not
treat it as one. [Call metadata](../construction/W08/reviews/attempt-1/reviewer/turn-01/summary.json).

Two separate findings from manual inspection:

- **Faithfulness:** the writer says Priya belongs **only** to #design-crew; the
  compiler also adds her to #general. She still does not belong to the launch
  channel, so her negative classification survives. This is less damaging than
  W06's loss of a missing-relationship negative, but still changes a fixed fact.
  The reviewer notices both memberships in its thinking without flagging the
  conflict with “only.”
- **Quality:** the compiler gives the intended message the text “Standup notes for
  today's launch check,” while the two actor-owned fire-reaction negatives concern
  a design review and marketing timeline. That introduces a possible lexical
  shortcut for a task intended to depend on author membership. It is not an
  invalidating condition or a measured solver effect. The reviewer considered the
  launch wording and dismissed it as natural context.

The actor belongs to #general and #product-launch, which contain all the story's
reaction-bearing messages. This avoids the specific seed omission seen in W06;
it is not a substitute for an actual native visibility result, which does not exist.

## W09 — absent workspace association behind a bot/channel reference

> What workspace is shown on the profile of the bot that belongs to the #incident-response channel?

Route: **Workspace → Workspace Membership → User → Conversation Membership → Conversation**.
The [writer](../construction/W09/story.md) declares absence through complementary
near misses:

| Subject | Seed facts | Why the full chain does not match |
|---|---|---|
| WatcherBot | Bot; Cascade Systems membership; member of #project-launch | Wrong channel |
| Dana Reyes | Nimbus Robotics membership; member of #incident-response | Not a bot |
| PulseBot | Bot; member of #incident-response; no workspace-membership record | Missing workspace association |

The [compiler](../construction/W09/compiled-1.json) preserves those facts and adds
ordinary filler. The actor is non-bot, so its added #incident-response membership
does not accidentally create a match. The
[Python check](../construction/W09/checks-1.json) returns an empty set; this audit's
replay agrees. PulseBot's row legitimately has a null workspace referent because
the specified association really is missing, unlike W10's null bindings.

The subsequent reviewer call returned a **read timeout**. Its
[saved metadata](../construction/W09/reviews/attempt-1/reviewer/turn-01/summary.json)
contains no native usage; there is no response, thinking text, verdict, or review
finding. This is a service-call failure, not evidence of rejecting an invalid case.

This remains a **database-consistent absence case whose native behavior is not
validated**. In particular:

- The request concerns a profile's displayed workspace, while the selector computes
  stored membership. The missing-association profile behavior must be established
  before treating that database absence as the solver-visible answer. No native
  W09 observations establish it here.
- The actor's workspace differs from the workspace hosting #incident-response;
  it has channel membership there but no workspace membership there. The supplied
  [workspace-scope audit](../../../../domains/slack/coverage/workspace_scope_audit.md)
  documents differences between actor-scoped listing and ID/name-addressed calls.
  Neither general discoverability nor total inaccessibility follows just from the
  seed. Native preflight was never reached.
- The annotation lists `teams.team_name` as an alternative answer-computation
  input, although the supplied domain contract says stored workspace names are
  not exposed by workspace lookup. Profile workspace IDs are the supported
  representation. This questionable annotation does not change the computed empty
  set, and is not an observed evaluator error.

The conceptual missing-association negative is useful, but this audit does not
upgrade the case to runtime-ready or claim that the compiler settled its API
representation. No decoy message gives away its test role.

## W10 — report admin/owner status of selected reactors

> Are the people who reacted with a rocket to the launch-checklist message, in the channel that has Priya as a member, workspace admins or owners?

Route: **Workspace Membership → User → Reaction → Message → Conversation → Conversation Membership**.
The [writer](../construction/W10/story.md) intends Alice and Ben. Alice is an admin;
Ben is neither admin nor owner. Their differing answers are deliberate: answering
“no” does not make Ben a nonmatch.

| Person | Identifying facts | Role |
|---|---|---|
| Alice | 🚀 on the checklist in the channel containing Priya | Match; admin |
| Ben | Same, plus an unrelated 👀 elsewhere | Match; neither admin nor owner |
| Chloe | 👍 instead of 🚀 on the checklist | Wrong emoji |
| Diego | 🚀 on a launch-party invitation | Wrong message |
| Elena | 🚀 on an identical checklist in a channel without Priya | Wrong channel membership |
| Farid | Shares Priya's channel but has no reaction | Missing reaction |

### Historical three-turn sequence

1. The compiler appends `channel_members → users` to look up the member's name
   “Priya.” The original checker demanded exact path length and rejected this.
   The extension retains the assigned route and expresses an existing condition;
   it is not an invented restriction. The initial rejection was a checker problem.
2. In response, the compiler shortens the path and filters the membership directly
   by `U_PRIYA`. The selector lock rejects this change.
3. The compiler returns exactly its first compilation, reproducing the old route
   error. Its [thinking summary](../construction/W10/compiler/turn-03/thinking.txt)
   explicitly struggles with changing versus preserving the locked selector and
   speculates incorrectly about which version was locked.

Sources: [check 1](../construction/W10/checks-1.json),
[check 2](../construction/W10/checks-2.json),
[check 3](../construction/W10/checks-3.json).
Across the three outputs, the seed, annotations and bindings never change. Attempt
2 changes only the selector; attempt 3 is identical to attempt 1. This is not
evidence of an impossible story. Faulty route feedback induced a repair loop, and
the compiler did not stop with the permitted conflict response.

### Separate compiler error exposed by the corrected checker

The route-prefix check was already corrected during the W02 work. Replaying W10
under today's checker accepts the original path extension but reveals an empty
declared-negative list. The compiler used **null** referents for Chloe, Diego,
Elena and Farid despite creating a `user_teams` record for every one of them.

Those are existing roots that fail a condition; the roots themselves are not absent.
The compiler's [first thinking summary](../construction/W10/compiler/turn-01/thinking.txt)
explicitly connects Chloe's wrong emoji to leaving her referent null, establishing
the conceptual mistake. The original run never reached this check because it
failed the earlier route check on every otherwise eligible attempt.

An **in-memory diagnostic** supplies only the four existing membership handles.
With the seed, original selector, annotations and supports unchanged, all current
mechanical checks pass and still select Alice and Ben. No modified case was saved
or executed. [Offline replay results](W08_W09_W10_offline_checks.json).

The concrete world retains each specified negative and contains no “ignore this”
decoy cues. One potential quality shortcut is introduced during compilation:
Priya authors the qualifying checklist, although the request requires only channel
membership. A solver could use that authorship cue instead of verifying membership
and still reach the right result here. No solver run measures whether that happens.
The actor also lacks membership in the marketing channel containing Elena's
negative; native readiness remains untested rather than assumed.
